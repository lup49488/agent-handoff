## 2. 本次审核新增的已确认问题

### P0（已修复）：Windows 非 UTF-8 控制台会让 `handoff status` 崩溃

在本机 PowerShell 的 `cp932` 输出编码下，以中文任务标题执行 `handoff init` 后再执行 `handoff status`，会触发：

```text
File "...\cli.py", line 47, in _echo
    print(msg)
UnicodeEncodeError: 'cp932' codec can't encode character '\u590d' ...
```

影响：状态包已成功创建，但用户无法读取状态；这会削弱中文 Windows 用户场景的恢复能力。

**受影响范围的实测结果，与初稿的推测不同。** 逐条复现后：

| 命令 | 结果 |
|---|---|
| `status`、`checkpoint --show` | 崩溃，exit 1 |
| `init`、`pack`、`verify`、`checkpoint`（写入） | 正常，exit 0 |

初稿建议验证 `init` / `status` / `checkpoint` / `pack` 四条路径，但 `init` 与 `pack`
并不回显用户文本，本就不在风险面上；真正会崩的 `checkpoint --show` 反而漏了。准确的
判据是**任何回显已记录文本的命令**——这还包括 `sessions`、`health`，以及 `runner`
中把 agent 输出直接写 `sys.stdout` 的 `_capture`，后者崩溃会打掉监督线程，比 `status`
崩溃更严重。

另一个佐证：`handoff event 文件已修改` 不崩溃，只显示乱码——这几个汉字都在 Shift-JIS
字表内，能编码；`复`（`\u590d`）是简体独有才触发异常。按字符集碰运气，所以兜底必须放在
输出层统一处理，而不是逐个命令排查。

**已实施的修复：** `main()` 入口调用 `_relax_console_encoding()`，对 `sys.stdout` /
`sys.stderr` 执行 `reconfigure(errors="replace")`。只放宽错误策略、不强制改成 UTF-8——
在 legacy 代码页控制台上强推 UTF-8 会把它本来能正常显示的文字也变成乱码。落盘数据全程
`encoding="utf-8"`（见 `store.py`），不受影响；控制台无法呈现的字符降级为 `?`，其余状态
照常可读。

**回归测试：** `tests/test_console_encoding.py`，以 `PYTHONIOENCODING=cp932` 子进程运行
真实 CLI（进程自身 stdout 的编码正是 bug 所在，进程内 fake 无法忠实复现）。三条用例在
移除修复后全部失败，加回后全部通过。全量回归 **294 passed**。

## 3. 已核验的竞品与真实差异

| 项目 | 已核验事实 | 对本项目的含义 |
|---|---|---|
| [agentswap](https://github.com/bojieli/agentswap) | 账号/提供商 failover 与原生 session teleport；读取和写入各 CLI session | 保持“保存可恢复工作状态，而非核心依赖私有 session 格式”的差异 |
| [paxl](https://github.com/pax-beehive/paxl) | 读取本地 session，并在 Claude/Codex 间 mirror；涉及 Codex 桌面端 | 不应宣称桌面兼容是独有优势；重点应是低耦合、可审计的状态包 |
| [AgentBridge](https://github.com/raysonmeng/agent-bridge) + [agent-quota-guard](https://github.com/raysonmeng/agent-quota-guard) | 提前预算（80/90/99% 三级阈值）、回合边界暂停、`wait_until_budget_refresh` 续接。两者配套但独立：AgentBridge 将 quota-guard 列为 companion，而 quota-guard 可单独使用，仅声明「若同时运行 Bridge 的预算调度，以 Bridge 为准」 | 可借鉴为 opt-in 的 quota guard，不能假设每个平台都能可靠提供额度 |
| [moshi-labs/handoff](https://github.com/moshi-labs/handoff) | `parser → NeutralSession → writer` 的 session 转换路线 | 这是不同技术路线；本项目应强调 repo-local handoff，而非复制它 |
| [agent-checkpoint](https://github.com/hotalexnet/agent-checkpoint) | repo-local checkpoint/resume Skill，跨代理 Markdown 状态；安装到 `~/.agents/skills/`。**其 Markdown 格式名即 `agent-handoff/v1`** | Skill UX 是直接竞争点；本项目的优势应是 CLI 监督、完整性校验、测试/命令/事件证据。命名冲突比 UX 竞争更需要先处理——搜索 “agent-handoff” 会同时命中两个项目 |

“resume-handoff”等名称并不唯一；在没有明确仓库 URL 前，不应把它们写入 feature matrix 或得出比较结论。

## 4. 下一版优先级

### P0 — 先修可靠性与可验证性

1. ~~修复并回归测试 Windows 非 UTF-8 控制台的中文 CLI 输出。~~ 已完成，见 §2。
2. 建立 20–50 次自动故障演练：quota、429、非零 crash、silent stall、半写 JSONL、遗留临时文件、锁竞争。
3. 每个场景验证：当前 Git 状态没有丢失、`handoff verify` 行为正确、下一 agent 只在包有效时启动。

### P1 — 证明 handoff 的价值

建立三个公开 demo task：小 bug、中型 feature、多文件 refactor。各在约 30%、60%、80% 进度强制中断，比较 baseline 与 handoff：

| 重复命令数 |  |  |
| 总恢复成本（tokens 或可说明的代理步骤） |  |  |
| 完成率与错误恢复率 |  |  |

预先声明运行模型、版本、任务提交 SHA、计量规则与失败注入点。只在有重复实验结果后宣传“减少恢复成本”的百分比。

### P2 — 扩展前做真实 adapter 验收

对 Pi、Gemini CLI、OpenCode 分别在小型 disposable repo 中确认：可启动命令、interactive/non-interactive 语义、真实失败字符串、停止/子进程行为、恢复命令和 session 可读边界。每确认一个，再将其从“内置但未验证”升级为“已验证”。

### P3 — 可选的提前 quota guard

仅在平台能提供可靠额度信息时，加入可配置的阈值前 checkpoint 提醒或干净暂停。默认不强制切换，不读取或转移凭据，并清楚披露 telemetry 来源与误差。

## 5. 不在当前路线中的范围

保持项目轻量：不做 Web dashboard、云账户、多 agent 团队编排、投票/Planner/Reviewer、RAG 记忆、复杂成本路由或通用 workflow engine。
